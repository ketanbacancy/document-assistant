# Document Assistant (RAG Chatbot)

A Laravel + React chatbot that answers questions grounded in your own PDF/DOCX/TXT/MD documents — **R**etrieval-**A**ugmented **G**eneration (RAG). Every chat is scoped to one document: pick a document, ask a question, and the answer is generated only from text retrieved out of that document, with the exact chunks it used shown alongside the answer.

Everything runs **locally and for free** except the final answer-generation step: embeddings and chart/figure reading both run through a local [Ollama](https://ollama.com/) install, so ingesting documents (however many, however large) never touches an external quota. Only the actual chat answer is generated by Google Gemini.

For a deeper, file-by-file walkthrough of both the ingestion and chat pipelines, see **[ARCHITECTURE.md](ARCHITECTURE.md)**.

## Features

- Multiple documents, each with its own isolated chat history — a document picker/switcher is always visible, so you can jump between documents without losing either one's conversation
- PDF chart/figure reading: pages containing a figure are rendered to an image and read by a local vision model, so chart data (bar/line chart values, etc.) that plain text extraction can't see becomes answerable too
- Answers stream in token-by-token as Gemini generates them
- Every answer shows which chunks it was based on, with a relevance score and excerpt
- Conversation history persists across page refreshes and is grouped by recency (Today / Previous 7 days / Older), like ChatGPT's sidebar
- No upload UI — documents are ingested via a console command, which is what makes bulk/offline ingestion of large reports (100+ pages) practical
- Ships with 3 documents already ingested (seeded straight into the database on setup) so you can try the app immediately without waiting on any ingestion

## How it works

### Ingestion (`php artisan document:ingest`)

```
Parse (text) ──┐
               ├─► Combine ─► Chunk ─► Embed (Ollama, local) ─► Store (SQLite)
Vision (charts)┘
```

1. **Parse** — the file's full text is extracted (`DocumentParserService`): `smalot/pdfparser` for PDF, `phpoffice/phpword` for DOCX, raw read for TXT/MD.
2. **Chart/figure vision** (PDF only) — `ChartVisionService` scans every page's extracted text for the literal word "FIGURE" (a caption heuristic). Each matching page is rendered to a PNG (via `scripts/render_pdf_page.py`, using PyMuPDF — nothing in PHP on Windows can rasterize a PDF page) and sent to a local vision model (`qwen2.5vl:3b` via Ollama) with a prompt asking it to transcribe the chart's data points as a terse list. Each page's render + describe step is independently fault-tolerant — one slow/failed page is logged and skipped, it never aborts the whole ingestion run.
3. **Combine** — the chart descriptions are appended to the end of the document's plain text (they are *not* interleaved onto their original page — a page's prose and its chart data end up as separate, later-retrievable chunks).
4. **Chunk** — `ChunkerService` splits the combined text into ~800-character chunks on paragraph boundaries (falling back to sentence boundaries for oversized paragraphs), with an 80-character overlap between consecutive chunks so context isn't lost at a boundary.
5. **Embed** — every chunk is embedded in batches via Ollama's `nomic-embed-text` model (`EmbeddingService`) — local, so there's no per-document quota to manage.
6. **Store** — each chunk's text + embedding vector are stored together in the `document_chunks` table (as JSON) — there's no external vector database. The document's `status` becomes `ready` with its final `chunk_count`.

### Chat (asking a question)

```
Question ─► Embed (Ollama) ─► Cosine-similarity search, scoped to the
            conversation's document ─► Build prompt (system instruction +
            retrieved chunks + conversation history) ─► Gemini generate/
            stream ─► Persist turn ─► Return answer + sources
```

- **Retrieval is document-scoped**: a conversation (`Conversation.document_id`) only ever searches chunks belonging to its own document (`VectorSearchService`). A brute-force cosine-similarity scan over every chunk of that one document is fast enough (sub-millisecond, since each document is at most a few hundred chunks) that no dedicated vector index is needed.
- **Generation** is a direct HTTP call to Gemini's `generateContent` / `streamGenerateContent` REST endpoints (`GeminiChatService`) — there's no official Gemini PHP SDK. The streaming endpoint is what lets the frontend render the answer token-by-token instead of waiting several seconds.
- The system prompt instructs the model to answer strictly from the retrieved context (or conversation history), refuse with a fixed "I don't have that information in *{document}*" line otherwise, and to connect directly-related figures sitting together in the context (e.g. a baseline + a reduction + the resulting total) rather than only answering the literal question.
- A Gemini 429 quota response is detected and surfaced as a clear "try again in N hour(s)" message instead of a generic error (`GeminiQuotaExceededException`).

### Frontend

- `App.jsx` fetches the list of ready documents (`GET /api/documents`) and tracks which one the active chat is scoped to, setting the browser tab title to match.
- `ChatWindow.jsx` shows a document picker when starting a new chat, and an always-visible "Chatting about *<document>*" bar with a dropdown to switch documents directly (switching starts a fresh conversation, since an existing conversation can't be re-pointed at a different document).
- `ConversationSidebar.jsx` lists past conversations grouped by recency, each showing which document it belongs to.

## Architecture at a glance

| Layer | Technology |
|---|---|
| Backend | Laravel 13 (PHP 8.3) |
| Frontend | React 19 + Tailwind CSS v4, bundled by Vite |
| Database | SQLite — stores documents, chunk text + embedding vectors, conversations, messages |
| Vector search | None external — cosine similarity computed in PHP over chunks already in SQLite |
| Embeddings | **Ollama**, local — `nomic-embed-text` |
| Chart/figure vision (PDF ingestion only) | **Ollama**, local — `qwen2.5vl:3b` + Python/PyMuPDF for page rendering |
| Chat generation | Google Gemini — `gemini-3.5-flash-lite` (configurable) |

## Prerequisites

- PHP 8.3+ with Composer
- Node.js 20+ with npm
- [Ollama](https://ollama.com/) installed and running locally, with `nomic-embed-text` pulled — required for every chat question, seeded documents included
- Python 3 with [PyMuPDF](https://pymupdf.readthedocs.io/) installed (`pip install pymupdf`), and Ollama's `qwen2.5vl:3b` model pulled — **only needed if you'll ingest a new PDF that contains charts/figures yourself**; using just the seeded documents, or ingesting plain-text PDFs/DOCX/TXT/MD, never invokes either
- A [Google AI Studio](https://aistudio.google.com/) API key (free tier is enough) — used only for the final chat-generation step

## Setup

1. **Clone and install dependencies**

   ```bash
   git clone <this-repo-url>
   cd document-assistant
   composer install
   npm install
   ```

2. **Pull the local Ollama model(s)**

   ```bash
   ollama pull nomic-embed-text
   ```

   This one is required no matter what — every chat question is embedded at query time, whether you're just chatting with the seeded documents or ingesting your own.

   ```bash
   ollama pull qwen2.5vl:3b
   ```

   This one is **optional** — only pull it if you plan to run `document:ingest` yourself on a PDF that contains charts/figures. If you're only using the 3 documents already seeded with this repo, you can skip it entirely.

   Confirm Ollama is reachable at `http://localhost:11434` (or wherever you've configured it):

   ```bash
   curl http://localhost:11434/api/tags
   ```

3. **Configure the environment**

   ```bash
   cp .env.example .env
   php artisan key:generate
   ```

   Then fill in `.env`:

   | Variable | Value |
   |---|---|
   | `GEMINI_API_KEY` | Your key from [aistudio.google.com](https://aistudio.google.com/) → Get API key |
   | `GEMINI_CHAT_MODEL` | e.g. `gemini-3.5-flash-lite` (any current Gemini model that supports `generateContent`) — defaults to this if left blank |
   | `OLLAMA_HOST` | `http://localhost:11434` (default if left blank) |
   | `OLLAMA_EMBEDDING_MODEL` | `nomic-embed-text` (default if left blank) |
   | `OLLAMA_VISION_MODEL` | `qwen2.5vl:3b` (default if left blank) |

   > If `GEMINI_CHAT_MODEL` ever returns a 404 "model not found," list the models your key currently has access to:
   > ```bash
   > curl -s "https://generativelanguage.googleapis.com/v1beta/models?key=$GEMINI_API_KEY" | grep '"name"'
   > ```

4. **Set up the database**

   ```bash
   touch database/database.sqlite
   php artisan migrate
   php artisan db:seed
   ```

   The seed step loads the **3 documents already shipped with this repo** (text, chunks, and their embedding vectors — see `database/seeders/data/*.json`) straight into the database, so you get a fully working, queryable app immediately. No re-ingestion, no chart-vision processing, no waiting — that expensive work only ever has to happen once. You only need to run `document:ingest` yourself for a *new* document you want to add on top of these (see below).

5. **Run the app**

   ```bash
   composer dev
   ```

   This runs the Laravel server, queue listener, and Vite dev server together. Visit **http://localhost:8000**.

   (Or run pieces separately: `php artisan serve` + `npm run dev`.)

## Ingesting a new document

The 3 documents that ship with this repo are already seeded into the database (see Setup step 4) — you only need this for a document you want to add yourself. There's no upload UI — documents are ingested via a console command, which is what makes practical ingestion of large reports (chart-reading a 200-page PDF is a multi-hour, CPU-bound job) possible:

```bash
# Place the file in storage/app/seed-documents/ first, then:
php artisan document:ingest my-report.pdf "My Report (Display Name)"

# Or pass an absolute path directly:
php artisan document:ingest /absolute/path/to/file.pdf

# Re-ingest a document that's already indexed:
php artisan document:ingest my-report.pdf --force
```

- The display name (2nd argument) defaults to the file's basename if omitted.
- If the file is a PDF, progress for each figure/chart page found is printed live: `[current/total] page N — reading chart(s)...` / `chart data found` / `no chart data` / `skipped (render/describe failed)`.
- A document already ingested with the same name is skipped unless `--force` is passed, in which case it's deleted and re-ingested from scratch.
- Ingestion time depends almost entirely on how many pages contain figures (plain-text pages are nearly instant; a PDF with no figure-marked pages at all finishes in seconds regardless of page count) and on your CPU, since the vision model runs CPU-bound unless you have a usable GPU.

### Sharing a newly ingested document with everyone else

Once you've ingested a new document and are happy with it, export it into the committed seed data so the next `db:seed` (a fresh clone, CI, production) picks it up too without re-running the vision/embedding work:

```bash
php artisan document:export-seed
git add database/seeders/data/
git commit -m "Add <document name> to seed data"
```

This overwrites `database/seeders/data/documents.json` and `document_chunks.json` with **everything** currently in your `documents`/`document_chunks` tables (not just the new one), so it's a full re-export, not an append.

## Usage

1. Open the app — if no documents are indexed yet, ingest one first (see above), then refresh.
2. Click **New chat**, then pick a document from the picker (or use the document switcher dropdown at the top of the chat window at any time).
3. Ask a question. The answer streams in, grounded only in the selected document; expand **Show sources** under any answer to see exactly which chunks it used and their relevance score.
4. Use the document switcher dropdown to jump to a different document — this starts a fresh conversation scoped to that document (an existing conversation can't be re-pointed at a different one).
5. Past conversations are listed in the sidebar, grouped by recency, each labeled with its document.

## Deploying to production

- **`php artisan migrate && php artisan db:seed` is enough to get production a working database** with the same ingested documents as everywhere else — the seed data (`database/seeders/data/*.json`) is committed to the repo, so there's no need to copy a database file around or re-run ingestion on the production box at all.
- **Ollama must still run wherever query-time embeddings happen**, even though the documents are pre-seeded — every chat message is embedded through `nomic-embed-text` before retrieval, so production needs its own local Ollama with that model pulled (`ollama pull nomic-embed-text`). There's no quota risk since it's local inference, unlike swapping in a hosted embeddings API.
- **The vision model (`qwen2.5vl:3b`) and Python/PyMuPDF are never needed in production** — they only run during `document:ingest`/`document:export-seed`, which you run once on your own machine before committing the result. Production only ever seeds already-computed chunk text and embeddings.
- Conversations and messages are **not** part of the seed data — they're live, per-environment chat history, and start empty in any freshly-seeded database.
